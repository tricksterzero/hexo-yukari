# hexo-yukari

日本語の記事に特化した [Hexo](https://hexo.io/) の関連記事プラグインです。辞書や人間による判定を使わず、記事のタイトルと本文だけから「**ゆかり**のある記事」を選びます。

## 特徴

- 辞書を使わずに日本語を語に分けます。漢字・カタカナ・英数字の連続を語とみなし、ひらがな(助詞や活用語尾)を捨てます。内容を表す語の多くは漢字かカタカナで書かれる、という日本語の書き方の性質を使います。辞書のバージョンや ICU の単語分割に結果が左右されません。
- 調整する値は表示件数だけです。関連の近さを両方向の順位で測り、閾値は持ちません。記事Aから見たBの順位と、Bから見たAの順位がどちらも高いほど近いとみなします([mutual proximity](https://jmlr.org/papers/v13/schnitzer12a.html))。多くの記事と似ている記事ばかりが並ぶ偏りを抑えつつ、片方向にしか上位に入らない記事にも関連記事を出せます。
- 同じシリーズばかりを並べません。近い候補から順に見て、すでに選んだどの記事よりも元の記事のほうに近い候補だけを採ります([HNSW](https://arxiv.org/abs/1603.09320) の近傍選択と同じ規則)。互いに似たシリーズの回で枠が埋まるのを防ぎます。候補は表示件数の4倍までに絞るので、関係の薄い記事は採りません。
- シリーズの一覧など、本文ですでにリンクしている記事は読者の目に入っているので、関連記事の欄には出しません。関連記事が見つからない記事でだけ、リンク済みの記事を予備として出します。
- 新しい記事を先に出し、古い記事にたどり着いた読者を、同じ話題の新しい記事へ案内します。
- 生成のたびに Markdown の本文から計算するので、キャッシュに左右されません。`hexo clean` をしなくても全記事の関連記事が更新されます。

## インストール

```bash
npm install hexo-yukari
```

[hexo-related-posts](https://github.com/sergeyzwezdin/hexo-related-posts) など、`page.related_posts` を設定する他のプラグインとは同時に使わないでください。

## 設定

Hexo ブログのプロジェクトの `_config.yml` に書きます。どれも省略できます。型の違う値は、警告を出して既定値で続けます。

```yaml
yukari:
  enable: true # false で無効にする(yukari: false と書いても同じ)
  count: 5     # 表示件数(0以上の整数)
  embedding:   # 意味ベクトル(下記)
    enable: false
    combine: false # true で本文の語と併用する
    device: cpu    # cpu / gpu / dml / webgpu(Linux では cuda も)
```

## 意味ベクトル(任意)

語の重なりの代わりに、または語の重なりと併せて、日本語の文章埋め込みモデル [ruri-v3-30m](https://huggingface.co/cl-nagoya/ruri-v3-30m)で記事の近さを測れます。語が重ならなくても話題の近い記事を拾えます(例: ゲーム用アプリのリリース記事と、そのゲームの記事)。本体はこのコンポーネントが無くても動き、依存関係も持ちません。

使うには、Hexo ブログのプロジェクトに [Transformers.js](https://github.com/huggingface/transformers.js) を入れ、`embedding.enable` を `true` にします。入っていなければ、警告を出して本文の語で判定します。動作を確かめたのは 4.3.0 です。Transformers.js は最初の生成のときに読み込むので、`hexo new` などの生成しないコマンドは遅くなりません。

```bash
npm install @huggingface/transformers@4.3.0
```

- **信号**: `combine: false` なら意味ベクトルだけ、`true` なら本文の語と意味ベクトルそれぞれの mutual proximity の平均で判定します。意味ベクトルを使うときは、語を共有しない記事も候補にします。ベクトルは全記事の平均を引いてから比べます(中心化)。
- **device**: Transformers.js の `device` にそのまま渡します。Windows の Node では `cpu`・`dml`(DirectML)・`webgpu` が使え、`gpu` は `dml` と `webgpu` から選ばれます。モデルを読み込めないか、計算の途中で失敗したら、警告を出して `cpu` で続けます。`cpu` でも失敗したときは、その生成は本文の語で判定します。372記事の実測(1回)は `cpu` 20.6秒、`dml` 12.2秒、`webgpu` 6.8秒でした。
- **キャッシュ**: 初回の生成でモデル(約147MB)を取得し、記事のベクトルとともに Hexo ブログのプロジェクトの `.yukari-cache/` に置きます。ベクトルはタイトルと本文から作った文章のハッシュで管理し、2回目以降は変わった記事だけを計算します。形の正しくない値は計算し直します。`.yukari-cache/` は `.gitignore` に入れてください。
- **結果の揺れ**: 同じ記事でも、device を変えたりベクトルを作り直したりすると、値が小数点以下5桁目付近で変わることがあります。順位が近い候補の並びが入れ替わりうるので、結果をそろえたいときはキャッシュを残してください。

## テーマとの連携

記事のページの `page.related_posts` に、関連記事の `path` の配列を入れます。[NexT](https://theme-next.js.org/) はこの形をそのまま表示できるので、テーマの設定で `related_posts.enable: true` にするだけで使えます。

```njk
{%- for path in page.related_posts %}
  {%- set post = site.posts.findOne({ path: path }) %}
  <a href="{{ url_for(post.path) }}">{{ post.title }}</a>
{%- endfor %}
```

## 仕組み

1. 各記事のタイトルと本文から、コード・タグプラグイン・HTML・URL を取り除きます。本文でリンク済みの記事を調べるときは、コードと HTML コメントの中のリンクを数えません。
2. 文字の種類の切れ目で語に分けます。3文字以上の漢字の連続は2文字ずつにも分け、`武器使用回数` と `使用回数` のような複合語の部分一致を拾います。1文字の漢字の直後がひらがななら、動詞・形容詞の語幹(`書く`・`良い`)とみなして捨てます。
3. 語ごとに TF-IDF の重みを付け、記事どうしのコサイン類似度を求めます。1記事にしか出ない語は使いません。全記事に出る語は重みが0になります。
4. 記事の組ごとに mutual proximity を求めます。記事Aと記事Bの値は、「Aから見てBより類似度が低く、かつBから見てAより類似度が低い記事」の数を全記事数で割ったものです(Schnitzer ら 2012、3.2.1節)。
5. 語を共有する記事(意味ベクトルを使うときは全記事)のうち、本文でリンク済みでない記事を、mutual proximity の高い順に並べます。同点は類似度、パスの順で決めます。
6. 上位 `count` の4倍までの候補を順に見て、すでに選んだどの記事との類似度よりも、元の記事との類似度が高い候補を `count` 件まで選びます(Malkov & Yashunin、arXiv:1603.09320 の Algorithm 4)。足りなければ、見送った候補を順に足します。
7. 選んだ記事を、元の記事より新しい記事、古い記事の順に、それぞれ mutual proximity の高い順で並べます。候補が無ければ、本文でリンク済みの記事を出します。

## 制約

- 数字の直後の漢字(`10回程度` の `回程度` など)は、後ろの語とつながったまま1語になります。
- 略語と正式名(`スマホ` と `スマートフォン`)は別の語として扱います。辞書を使わないためです。
- 語の重なりで判定するので、本文が短い記事や、他の記事と語をほとんど共有しない記事では、関連の薄い記事が並びます。本文の語だけで判定するときは、語を1つでも共有する記事が無ければ、関連記事なしになります。
- 全記事に出る語は重みが0になるので、記事が2件しかないブログでは、本文の語だけでは関連記事が出ません。
- mutual proximity は記事の組ごとに全記事を数えるので、計算量は記事数の3乗に比例します。
- 意味ベクトルは、同じ話題の記事どうしをより強く結びつけます。シリーズものでは、多様性の処理をしても、関連記事が同じシリーズの記事で埋まりやすくなります。
- 多様性の処理で、上位 `count` 件に入らない記事(最大で `count` の4倍の順位)が選ばれることがあります。
